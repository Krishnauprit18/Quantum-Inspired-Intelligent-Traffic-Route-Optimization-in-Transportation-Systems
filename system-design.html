01Scope, actors & the one-line goal

Before boxes and arrows: who touches this system, what they push a button to get, and the single sentence the whole design serves.

The goal in one line Given a city graph with live edge weights and a fleet with constraints, produce near-optimal routes fast enough to act on, prove with benchmarks that QPSO converges better and cheaper than classical baselines, and keep re-solving as traffic moves.

02Functional requirements

What the system must be able to do. Numbered so LLD and tests can cite them.

  1. FR-1 Import a network. Ingest an OSM extract for a city → build a directed weighted graph (nodes = intersections/depots, edges = road segments with length, free-flow time, capacity, road class). Produce a versioned contraction-hierarchy (CH) build.
  2. FR-2 Keep weights live. Consume a stream of segment speeds / incidents and update edge travel-time weights; expose the current weight set as an immutable, versioned epoch.
  3. FR-3 Solve a VRP. Accept a problem spec (fleet size & capacity, depot(s), stops, time windows, max route duration, objective, time budget) and return one route per vehicle that visits every stop once.
  4. FR-4 Solve shortest path. Return a traffic-aware fastest path and ETA for a single origin–destination pair, synchronously.
  5. FR-5 Anytime results. While solving, publish the best-so-far solution and its cost; a caller with a 200 ms budget still gets a usable answer.
  6. FR-6 Re-optimize on change. When weights change materially or a stop is added/cancelled, re-solve using the previous solution as a warm start; report the delta.
  7. FR-7 Constraint handling. Enforce capacity, time windows and route-duration limits; never return an infeasible route silently — either repair it or flag the violation.
  8. FR-8 Pluggable algorithms. Same problem spec runnable through QPSO, PSO, GA, ACO, and OR-Tools / exact CH, selected by config.
  9. FR-9 Benchmark. Run a dataset × algorithm × seed matrix; emit per-run metrics, convergence traces and a statistical comparison report.
  10. FR-10 Visualize. Render routes and congestion on a map; show cost breakdown (time, distance, load, violations) and a convergence chart.
  11. FR-11 Simulation mode. Drive weights from SUMO instead of a live feed; let a planner edit the network and demand and compare scenarios.
  12. FR-12 Multi-tenant isolation. A tenant sees only its own networks, jobs and results; quotas are enforced per tenant.

04Back-of-envelope capacity estimation

Rough figures for one metro. The point is the method and the order of magnitude, not three-digit precision.

Graph size & memory

  • OSM metro extract ≈ 2×105 nodes, 5×105 directed edges.
  • Per edge: src, dst, length, free_flow_t, live_t, class, flags ≈ 64 B → ~32 MB base.
  • CH shortcuts inflate edges ~3× → ~100 MB resident graph. Comfortably fits in RAM → replicate the whole graph to every worker; no distributed graph store on the hot path.

Traffic ingestion

  • Speeds update for ~20% of edges every 30 s → 105 updates / 30 s ≈ ~3.3k msg/s, ~100 B each ≈ 330 KB/s. Trivial for Kafka; one partition per city is enough.
  • Raw GPS probe retention: 7 days, then aggregate to segment speeds and drop raw — ~28 GB/day raw → downsampled to ~1 GB/day.

Optimization load

  • 5,000 vehicles, mean re-plan every 5 min → 5000 / 300 ≈ ~17 VRP req/s; plus ~200 rps ad-hoc shortest-path at peak.
  • One 50-stop QPSO run: 40 particles × 300 iters × fitness eval (~50 CH matrix lookups @ ~5 µs) ≈ ~3 CPU-s single-thread → ~0.5 s wall on 8 cores.
  • Steady compute: 17 × 0.5 ≈ 9 cores; 3× peak → ~30 cores → ~4 worker nodes (8 vCPU) with autoscale headroom.

Storage

  • Solution bundle ~5 KB. 17/s × 86,400 ≈ 1.5M/day → ~7.5 GB/day; 30–90 day retention in TimescaleDB + object store.
  • CH graph builds: ~150 MB each, keep last ~5 per city in object storage.
  • Benchmark artifacts: bursty, ~GBs per campaign, cold storage.
What the numbers tell the design The graph is small enough to replicate, so the hard problem is CPU for the swarm, not data distribution. Scale = “add stateless workers,” and the queue depth is the autoscaling signal.

06High-level design

Stateless request/API tier at the edge, an async job plane, a CPU-heavy optimization plane, and a streaming weight pipeline feeding an in-RAM graph. Data stores at the bottom.

Component responsibilities

API Gateway (APISIX)

TLS termination, OIDC token check, per-tenant rate limit & quota, JSON-schema validation, WAF (Coraza + OWASP CRS), request IDs. No business logic.

Routing Orchestrator

Owns job state machine (queued→running→done/cancelled/failed), builds the distance matrix via Graph Service, enqueues work, fans in anytime incumbents, persists solutions, drives re-optimization with warm starts.

Graph Service

Loads a CH build + current weight epoch into RAM; answers ShortestPath and many-to-many Matrix in microseconds; hot-swaps epochs atomically behind a pointer.

Network Builder

Batch: OSM extract → PostGIS topology → CH preprocessing → immutable build in MinIO. Emits network.build.ready.

Weight Updater

Consumes Kafka speed/incident events, blends with free-flow model, writes weight history to TimescaleDB, publishes a new immutable epoch array + bumps the Valkey pointer.

QPSO Worker Pool

Pulls a job, runs the swarm loop (update → decode → repair → evaluate), publishes best-so-far every K iterations, stops on budget/stagnation. Stateless besides the replicated graph.

Fitness Eval Actors

Ray actors that cost a batch of candidate encodings against the graph in parallel — the one place raw core count buys speed.

Benchmark Service

Expands a campaign matrix into jobs, pins container digest + seed + dataset hash, collects curves, runs Wilcoxon + Holm, writes a report bundle.

Why a weight epoch and not a mutable table on the hot path Workers must cost thousands of candidates against a consistent weight set. An epoch is an immutable array snapshot identified by id; a run pins one epoch start to finish, so results are reproducible and no locking is needed while weights keep flowing.

08Deep dives

The five decisions the design actually turns on.

8.1  Graph representation & fast queries

VRP fitness = sum of shortest-path times between many node pairs, evaluated thousands of times per run. Naive Dijkstra per pair is far too slow. We precompute a contraction hierarchy offline; online queries become near-constant-time, and many-to-many matrices use the bucket-based CH algorithm.

Option A — build our own CH

Full control of the weight model and epoch hot-swap; more preprocessing code to own and test.

Option B — embed GraphHopper / OSRM

Battle-tested CH + matrix APIs, OSM import for free; weight changes need a partial rebuild or its custom-model hooks.

Decision Use GraphHopper as the routing core (Apache-2.0, flexible custom weighting, no full rebuild for weight-parameter changes) behind our own Graph Service facade. Keep a thin in-house CH as a fallback and for the “implement the algorithm ourselves” deliverable. OSRM stays as a low-latency baseline in benchmarks.

8.2  Dynamic weights: streaming pipeline & epochs

  • Blend, don’t overwrite: live_t = max(free_flow_t, observed_t) smoothed with an EWMA so a single bad probe can’t spike an edge.
  • Gap fill: edges with no recent probe fall back to a class-based congestion factor by time-of-day.
  • Atomic swap: Graph Service watches the pointer; on change it loads the new epoch beside the old and flips a reference — in-flight queries finish on the old one.
  • Staleness guard: if the newest epoch is older than 5 min, responses carry weights_stale: true.

8.3  The distributed QPSO engine

QPSO drops PSO’s velocity term: each particle’s next position is drawn from a distribution around a local attractor between its own best and the global best, with a mean best (mbest) term that widens or narrows the search. It has one main knob (the contraction–expansion coefficient β), converges fast, and escapes local optima better than PSO — a good fit for a time-budgeted service.

Parallelism model

Island model: N worker processes each run an independent sub-swarm on the replicated graph; every M iterations they exchange their best encoding through the orchestrator (ring topology). Within a worker, candidate evaluation is farmed to Ray actors across cores.

Anytime contract

Every K iterations a worker publishes (best_cost, encoding) to job:{id}:events. The orchestrator keeps the global incumbent and serves it on any poll. Cancel = stop iterating, freeze incumbent.

Warm starts

Re-optimization seeds ~30% of the swarm from the parent solution (with the changed stop inserted greedily) and the rest random — fast convergence without losing diversity.

Determinism

Per-worker RNG seeded from job.seed + worker_index; exchange schedule fixed. Same seed + same epoch + same container digest → same result.

8.4  The real-time re-optimization loop

  • Triggers: new weight epoch where the current routes’ cost rises > τ%, a stop added/cancelled, or a vehicle goes off-plan.
  • Debounce: at most one re-optimization per fleet per 60 s; triggers within the window coalesce.
  • Idempotency: a re-opt job carries parent_job_id + trigger hash; a duplicate trigger returns the existing child job.
  • Regret metric: report cost(new) − cost(old under new weights) so operators see the value of re-planning, and benchmarks can score responsiveness.

8.5  Caching & consistency

Cache keyed by exact epoch

Always correct, but hit rate collapses because the epoch changes every ~30 s.

Cache keyed by epoch bucket (e.g. 60 s)

High hit rate for the shortest-path endpoint; a route can be up to one bucket stale.

Decision Bucket the epoch for the /v1/route cache (TTL 60 s, bucket 60 s) — commuters tolerate a one-minute-old route. VRP jobs never use the cache; they pin one exact epoch for the whole run. Cache is Valkey, invalidation is just TTL.

8.6  Scaling the worker pool

  • Jobs land on a queue (Kafka topic optimize.jobs, partitioned by city); workers are a consumer group.
  • KEDA autoscales the worker Deployment on queue lag and CPU; scale-to-min (not zero) keeps the graph warm.
  • Each city’s graph is ~100 MB; a worker pod pins one or a few cities to bound memory. Job routing respects that affinity.
  • Back-pressure: if lag exceeds a ceiling, the gateway returns 429 with Retry-After rather than letting budgets silently blow out.

09Low-level design

The optimization core as classes, the request lifecycle as steps, and the QPSO update rule as code. Language-agnostic but Python-leaning (NumPy + Ray).

Class model — optimization-core

Request lifecycle — POST /v1/optimize

  1. client → gateway Request hits APISIX: TLS, JWT + scope check, schema validation, tenant rate-limit, Idempotency-Key lookup. Duplicate key → return the prior job_id.
  2. gateway → orchestrator (gRPC/mTLS) Orchestrator validates nodes exist in city, pins ch_build + current weight_epoch, writes optimize_job(status=queued, seed), returns 202.
  3. orchestrator → Graph Service Request the many-to-many Matrix for all depot+stop nodes at the pinned epoch. Cache the matrix on the job.
  4. orchestrator → Kafka optimize.jobs Enqueue a job message (problem ref, matrix ref, algorithm, budget, seed). Set status=running.
  5. workers (consumer group) K island workers pick up the job; each builds a sub-swarm, seeds RNG from seed + index, warm-starts if parent_job_id set.
  6. worker ↔ Ray actors Each iteration: QPSO position update → decode → repair → cost_batch() across cores → update pbest/gbest; every M iters exchange best via orchestrator.
  7. worker → Valkey pub/sub Every K iters publish the incumbent to job:{id}:events; orchestrator keeps the global best and mirrors it to job:{id}:state.
  8. client → orchestrator GET /v1/optimize/{job_id} (long-poll or SSE) always returns the current incumbent + convergence trace.
  9. termination On budget/stagnation/target, workers stop; orchestrator writes final solution + route_leg rows, marks is_final, sets status=done, emits optimize.completed, appends audit_log.

QPSO update rule (per iteration)

# x: swarm positions  (P x D real matrix, D = number of stops)
# pbest: per-particle best positions ; gbest: global best
mbest = pbest.mean(axis=0)                          # mean of personal bests
beta  = beta_max - (beta_max - beta_min) * it / max_it   # 1.0 -> 0.5

for i in range(P):
    phi   = rng.random(D)
    p_att = phi * pbest[i] + (1.0 - phi) * gbest    # local attractor
    u     = rng.random(D)
    L     = 2.0 * beta * np.abs(mbest - x[i])       # well width
    sign  = np.where(rng.random(D) < 0.5, 1.0, -1.0)
    x[i]  = p_att + sign * L * np.log(1.0 / u)      # delta-potential-well draw
    x[i]  = np.clip(x[i], lo, hi)

routes = [encoding.decode(x[i]) for i in range(P)]     # random-key -> giant tour -> split
routes = [repair(r) for r in routes]
costs  = evaluator.cost_batch(routes)              # parallel; travel time + penalties
swarm.update_bests(costs)                          # pbest / gbest
if it % K == 0: callback.on_incumbent(it, swarm.gbest_cost, swarm.gbest)

Cost function: Σ leg_travel_time(epoch) + λ₁·capacity_overflow + λ₂·time_window_lateness + λ₃·duration_overflow. Penalty weights λ ramp with iteration so early search explores, late search is feasible.

Concurrency, failure & idempotency

  • Worker crash: Kafka offset not committed until an incumbent is published → job is redelivered; island diversity means one lost sub-swarm doesn’t fail the job.
  • Orchestrator crash: job state is in Postgres + Valkey, not memory; a new instance resumes fan-in from job:{id}:events.
  • Duplicate submit: Idempotency-Key unique index on optimize_job; second insert returns the first row.
  • Matrix build fails: job → failed with an RFC-7807 reason; no partial solution persisted.
  • Poison job: after 3 redeliveries → dead-letter topic + alert.

10Security — MNC-grade

Zero-trust between services, least privilege for people, a signed supply chain, and GPS data treated as personal data. All controls are open-source tooling.

Identity & access

  • AuthN: Keycloak OIDC; short-lived JWTs (10 min) + refresh; service-to-service identity via Linkerd mTLS (SPIFFE-style pod identity). No service accepts plaintext.
  • AuthZ: scoped tokens (optimize:write, network:read, benchmark:run, admin) checked at the gateway; fine-grained rules (tenant isolation, per-resource) as OPA policies evaluated in the orchestrator.
  • Multi-tenancy: every query is tenant-scoped in code and enforced again by Postgres row-level security; benchmark and admin actions are separate roles.

Accepted trade-offs

  • Replicated graph wastes RAM but removes a distributed store from the hot path — worth it at this scale.
  • Anytime QPSO may return a slightly sub-optimal route under a tight budget; we surface the gap rather than block.
  • Eventual weights mean a route can be tens of seconds stale; acceptable for routing, flagged in the response.
  • Single region in v1 — simpler ops; DR is warm-standby, RPO ~5 min.

14Benchmarking methodology

Deliverable 5 lives or dies here: a fair, reproducible comparison of QPSO against classical metaheuristics and exact methods.

Datasets

  • CVRPLIB (X, Golden); Solomon VRPTW (C / R / RC); Gehring–Homberger 200–1000 for scale.
  • One real OSM city instance with demand sampled from GPS aggregates — the “realistic large-scale scenario” the PS asks for.

Baselines

  • Classical PSO, GA, ACO (our implementations, shared eval/repair); Google OR-Tools GLS; CH / Dijkstra exact for shortest path; LKH-3 where tractable.

Metrics

  • Cost, and % gap to best-known; time-to-target (s to reach ≤2% gap); convergence curve (cost vs wall-clock); success rate; scalability curve (n vs time); re-opt regret under a scripted weight change.

Protocol

  • 30 seeds per cell; identical time budget across algorithms; report mean ± 95% CI.
  • Wilcoxon signed-rank + Holm–Bonferroni correction; report effect size, not just p-values.
  • Fixed hardware, pinned container digest, logged seeds, content-hashed datasets → a run reproduces from benchmark/run.yaml.

16Implementation roadmap

Three phases, each ending on something demonstrable. The PS deliverables map straight onto them.

Phase 0 — core (wks 1–4)

Deliverables 1–3.

  • OSM → PostGIS graph + CH build (static weights)
  • Mathematical model: objective + penalised constraints, decision vars
  • QPSO engine + encoding/split + repair; PSO baseline
  • CLI; Solomon / CVRPLIB benchmark vs OR-Tools + PSO

Phase 1 — platform (wks 5–8)

Deliverable 4.

  • FastAPI service + async jobs + Valkey + Graph Service
  • React + MapLibre UI: routes, congestion, convergence chart
  • SUMO feed → live weight epochs; re-optimization loop
  • docker compose one-command bring-up

Phase 2 — scale & hardening (wks 9–12)

Deliverable 5.

  • Kafka ingestion; Ray island workers; KEDA autoscale
  • K8s + Argo CD; Keycloak + OPA; mesh mTLS; OTel stack
  • Supply-chain + runtime security gates
  • Large real-city demo + full benchmark report with significance tests
Definition of done for the PS A running platform that imports a real city, holds it as a live weighted graph, returns near-optimal routes under changing traffic through a QPSO engine, shows them on a map, and ships a benchmark report where QPSO’s convergence and solution quality are compared — with statistics — against PSO, GA, ACO, OR-Tools and exact methods.
